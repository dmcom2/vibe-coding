오늘 나오는 용어 미리보기

외우지 마세요 — 눈에만 익혀 두면 수업이 술술 풀립니다

📌 WBS · 마일스톤

일을 단계 → 작업으로 나눈 목록(작업 분해 구조)과 번호(3.2 등). 마일스톤은 기간이 0인 이정표(설계 확정, 정식 출시).

📌 선행 관계 · 지연/겹침

"A가 끝나야 B 시작". +2는 끝나고 2근무일 뒤 시작, −5는 끝나기 5근무일 전부터 겹쳐 시작합니다.

📌 여유 · 주공정

출시일을 늦추지 않고 미룰 수 있는 근무일 수가 여유. 여유가 0인 작업의 사슬이 주공정(Critical Path)입니다.

📌 기준선

승인받은 처음 계획을 사진처럼 저장해 둔 것. 지금 일정과 비교해 "몇 일 늦어졌나"를 셉니다.

📌 획득가치 · SPI

계획상 지금까지 했어야 할 일(PV)과 실제로 한 일(EV)을 작업량으로 비교. SPI = EV ÷ PV, 1보다 작으면 늦음.

📌 투입률 · 인일

한 사람이 그 작업에 쓰는 시간 비율(50% 등). 기간 × 투입률이 작업량(인일)이고, 한 사람의 투입률 합이 100%를 넘으면 과부하.

핵심 기술 ① — 근무일 번호와 자동 일정 (전진 계산)

주말·휴일을 뺀 날에만 번호를 매기면, "3일 뒤"가 그냥 +3이 된다
// 근무일에만 0, 1, 2 … 번호를 붙인다 for (let d = from; d <= to; d++) { idxOf.set(d, days.length); // 쉬는 날 = 다음 근무일 번호 if (isWork(d)) days.push(d); } const idx = d => idxOf.get(d); // 날짜 → 번호 const dayOf = i => days[i]; // 번호 → 날짜 // isWork = 월~금 이면서 휴일 목록에 없음
// 선행 작업 순서(위상 정렬)대로 시작 · 끝 계산 for (const t of topo(tasks)) { let S = idx(프로젝트 시작일); if (t.preds.length) S = Math.max(...t.preds.map(p => R[p.id].F + (t가 마일스톤 ? 0 : 1) + p.lag)); if (t.nb) S = Math.max(S, idx(t.nb)); // 시작 제약 R[t.id] = { S, F: S + t.dur - 1 }; // 마일스톤은 F = S }
📅 완성 예제 기준 프로젝트는 2026.08.03(월)에 시작해 현재 계획으로 2027.01.04(월)에 출시합니다. '요구사항 정의'(10근무일 계획)는 8/17 광복절 대체휴일을 건너뛰어 8/10~8/21이 아니라 8/24에 끝나고, 기간이 12일로 늘어난 지금은 8/26에 끝납니다.

핵심 기술 ② — 주공정 (후진 계산과 여유일)

끝에서부터 거꾸로 "늦어도 언제까지 시작해야 하나"를 구하면, 빠른 시작과의 차이가 여유다
// 출시일(PF)에서 거꾸로: 가장 늦은 끝 · 시작 for (const t of topo(tasks).reverse()) { const r = R[t.id], ss = 후행작업들(t); r.LF = ss.length ? Math.min(...ss.map(x => R[x.id].LS - gap(x, lag))) : PF; r.LS = r.LF - t.dur + 1; r.float = r.LS - r.S; // 여유(근무일) r.crit = r.float <= 0; // 주공정 }
// 화살표도 주공정이면 빨간색: // 둘 다 주공정이고, 이 연결이 실제로 시작을 결정할 때 const driving = rb.S === ra.F + gap(t, p.lag); cls = ra.crit && rb.crit && driving ? 'crit' : ''; // 위상 정렬 중 방문 중인 작업을 다시 만나면 // → 순환 관계 → 연결을 막는다
🚨 완성 예제 기준 주공정은 킥오프 → 요구사항 → 기획 승인 → UX 리서치 → UI 디자인 시스템 → 공통 UI → 화면 개발 → API 연동 → 개발 완료 → 통합 테스트 → 인수 테스트 → 정식 출시의 12개입니다. 반면 '관리자 화면'은 여유가 30일, '테스트 계획'은 34일이나 됩니다.

핵심 기술 ③ — 기준선 비교와 획득가치(SPI)

"얼마나 했나"가 아니라 "해야 했던 만큼 했나" — 계획 진척률과 실적 진척률을 작업량으로 비교한다
// 기준선 계획상 기준일까지 지났어야 할 비율 const plannedPct = (S, dur, dd) => clamp((dd - S) / dur, 0, 1); // 지연 = 기준선 계획보다 10%p 이상 뒤처짐 if (t.pct >= 100) return '완료'; if (basePlanned(t) * 100 - t.pct >= 10) return '지연'; return t.pct > 0 ? '진행 중' : '대기';
// 작업량(인일) = 기준선 기간 × 투입률 const bac = t => base[t.id].dur * t.alloc / 100; PV = sum(tasks.map(t => bac(t) * basePlanned(t))); // 계획 EV = sum(tasks.map(t => bac(t) * t.pct / 100)); // 실적 SPI = EV / PV; // 1보다 작으면 늦음 // 기준선 대비 차이 = 지금 끝 − 기준선 끝 (근무일)
📊 완성 예제 기준(상태 기준일 10/14) 전체 작업량 201인일 중 계획은 99.0, 실적은 77.8로 진척률 39%, SPI 0.79입니다. 지연 작업은 7개(주공정 위 2개)이고, 마일스톤은 설계 확정 +5, 개발 완료 · 정식 출시 +8근무일로 기준선(12/21)보다 늦습니다.

핵심 기술 ④ — 영향 분석과 과부하 해소

"만약 ~라면?"은 복사본에서 다시 계산해 비교하면 된다
// 이 작업이 n일 늦으면: 복사본에서 기간 +n function impact(t, n) { const ts = clone(tasks); ts.find(x => x.id === t.id).dur += n; const R = schedule(ts); return { slip: R.PF - 지금.PF, // 출시일 변화 moved: 시작이 바뀐 작업들 }; } // 대략 max(0, n − 여유)와 같다
// 담당자별 근무일마다 투입률 합 load[who][i] += t.alloc; // S ≤ i ≤ F // 100% 초과가 이어진 구간 = 과부하 // 해소안: 겹친 작업 중 '아직 시작 전'이고 // 여유가 가장 큰 작업을, 나머지가 끝난 다음 날로 cand = 겹친작업.sort((a, b) => (a.pct > 0) - (b.pct > 0) || b.float - a.float)[0]; slip = Math.max(0, 미루는날 - cand.float);
⚡ 완성 예제 기준 '인증 · 회원 API'(여유 4일)가 5일 늦으면 출시일 +1일, 10일이면 +6일, 주공정인 '화면 개발'은 5일 늦으면 그대로 +5일입니다. 윤프론트는 10/6~10/22에 150% 과부하 — 해소안은 '관리자 화면'을 11/18로 30일 미루는 것이고, 여유가 30일이라 출시일 영향 없음입니다.

핵심 기술 ⑤ — 끌어서 고치기와 범위 추가 미리보기

마우스 조작도 결국 데이터 한 칸을 바꾸고 다시 계산하는 것 — 그리고 되돌릴 수 있어야 한다
// 막대를 끌어 놓으면: 시작 제약(nb)으로 저장 const want = idx(놓은 날), early = earliestStart(t); t.nb = want <= early ? null : toISO(놓은 날); // 선행보다 앞이면 제약 없이 → 가능한 가장 빠른 날 // 오른쪽 끝 = 기간, ▲ = 진척률(5% 단위) // ○ 끌어 다른 막대에 놓기 = 선행 연결 (순환이면 거절) commit(); // 스냅숏 기록(최대 60) → Ctrl+Z
// CSV: 복사본에 먼저 넣어 보고 출시일 변화를 보여 줌 const ts = clone(tasks); 새 작업 추가; 선행 = WBS 번호 또는 같은 파일의 작업명; 후행 = 기존 작업이 새 작업을 기다리게 연결; const pf = schedule(ts).PF; // 순환이면 오류 표시 미리보기(`출시일 ${지금} → ${pf}`); // 예전 형식(시작일 · 종료일)은 근무일 기간 + 시작 제약으로

날짜는 UTC 기준 날짜 번호로 계산(시간대 문제 방지) 전진 계산 (가장 빠른 시작 S · 끝 F) - 선행 순서대로(위상 정렬, 순환이면 오류) - S = 선행마다 (선행의 F + 간격 + 지연일) 중 최댓값, 선행이 없으면 시작일 번호 · 간격 = 후행이 작업이면 1, 마일스톤이면 0 · 시작 제약이 있으면 max(S, 제약일 번호) (마일스톤은 제약 무시) - F = S + 기간 − 1, 마일스톤은 F = S - 출시일(PF) = 모든 F의 최댓값, 단계 줄 = 자식의 최소 S ~ 최대 F 후진 계산 · 주공정 - 선행 순서의 역순으로: LF = 후행마다 (후행의 LS − 간격 − 지연일) 중 최솟값, 후행이 없으면 PF - LS = LF − 기간 + 1 (마일스톤은 LS = LF), 여유 = LS − S, 여유 ≤ 0이면 주공정 기준선 · 상태 · 획득가치 - 기준선 차이 = 지금 F − 기준선 종료일 번호 (+면 늦음) - 계획 진척률(시작 S, 기간 d, 기준일 번호 dd) = clamp((dd − S) ÷ d, 0, 1), 기간 0이면 dd > S일 때 1 - 상태: 진척 100 → 완료, (기준선 계획 진척률 × 100 − 진척률) ≥ 지연 기준 → 지연, 진척 > 0 → 진행 중, 그 외 대기 - 작업량(BAC) = 기준선 기간 × 투입률 ÷ 100 (마일스톤 0) - PV = Σ 작업량 × 기준선 계획 진척률, EV = Σ 작업량 × 진척률 ÷ 100, SPI = EV ÷ PV, 전체 진척률 = EV ÷ ΣBAC - 단계 진척률 = 자식 작업의 작업량 가중 평균 - S커브: 매주 금요일(프로젝트 시작 주부터) 그날까지 포함한 누적 PV — 기준선 계획 · 현재 계획(현재 S와 기간) 영향 분석 · 리소스 - 영향 분석: 복사본에서 그 작업 기간 + n(마일스톤은 선행 지연일 + n)으로 다시 계산 → 출시일 차이, 시작이 바뀐 작업 - 부하: 담당자별로 작업의 S~F 근무일마다 투입률을 더함 (마일스톤 제외) - 과부하: 100 초과가 이어진 근무일 구간, 구간과 겹친 그 사람의 작업들 - 해소안: 겹친 작업 중 (진척 0인 것 먼저 → 여유 큰 순 → 늦게 시작하는 순) 첫 작업을, 나머지 겹친 작업의 최대 F + 1로 미룸 → 미루는 날 수, 출시 영향 = max(0, 미루는 날 − 여유) - 적용하면 그 작업에 시작 제약을 걸고 다시 계산 ■ 5. 샘플 프로젝트 (숫자를 바꾸지 마세요) 기본값 - 이름 '고객 포털 v2 구축', 시작일 2026-08-03, 상태 기준일 2026-10-14, 지연 기준 10%p - 휴일: 2026-08-17, 2026-09-24, 2026-09-25, 2026-10-05, 2026-10-09, 2026-12-25, 2027-01-01, 2027-02-08, 2027-02-09, 2027-03-01 - 프롬프트 해설 — 왜 잘 작동했을까?

앞 슬라이드 프롬프트를 분석해 "AI에게 일정 로직을 시키는 법"을 배웁니다

POINT 1 — 저장할 것과 계산할 것을 나눈다

"작업에 날짜를 저장하지 않는다"는 한 줄이 핵심입니다. 날짜를 저장하면 AI는 앞 작업을 옮겨도 뒤 작업을 그대로 두는 간트를 만듭니다.

POINT 2 — 기준 날짜를 고정한다

'오늘'을 기준으로 하면 수업 날마다 지연 개수가 달라집니다. 상태 기준일을 설정값으로 두어 모두 같은 결과를 봅니다.

POINT 3 — 경계 조건을 숫자로

"끝난 다음 날 시작(+1), 마일스톤은 같은 날(+0)", "쉬는 날은 다음 근무일 번호"처럼 하루 차이를 적어야 날짜가 하루씩 어긋나지 않습니다.

POINT 4 — "만약"은 복사본으로

영향 분석 · CSV 미리보기 모두 복사본에서 다시 계산해 비교하라고 적었습니다. 원본을 건드리지 않으니 미리보기가 안전합니다.

✏️ 비교해 보기
❌ 막연한 요청

"작업 간 의존성을 지원하는 간트 차트를 만들어줘."

✅ 구체적인 요청

"시작 = 선행마다 (선행 끝 + 1 + 지연일)의 최댓값, 근무일 번호로 계산하고, 여유 = 가장 늦은 시작 − 가장 빠른 시작이 0이면 빨간색으로."

자주 막히는 문제 & 해결법

여기서 멈추는 게 정상입니다 — 옆 사람도 같은 곳에서 막혀 있어요
📆 "날짜가 하루씩 어긋나요"

시간대 때문에 날짜 계산이 밀리거나, 번호를 매기는 순서가 틀린 경우입니다. "날짜는 UTC 날짜 번호로, 근무일 번호는 push 하기 전에 기록해줘"라고 요청하세요.

🔗 "앞 작업을 늘려도 뒤 작업이 그대로예요"

작업에 시작일을 저장하고 있습니다. "시작일은 저장하지 말고 선행 작업의 끝에서 매번 계산해줘"라고 요청하세요.

♾️ "연결했더니 화면이 멈춰요"

A→B→A 같은 순환이 생겼습니다. "연결하기 전에 순환이 생기는지 검사하고, 생기면 거절해줘"를 추가하세요.

📊 "지연 개수가 매일 달라져요"

오늘 날짜로 판정하고 있습니다. "상태 기준일을 설정값으로 두고 그 날짜로 계획 진척률을 계산해줘"라고 요청하세요.

🤖 만능 해결법: F12 → Console의 빨간 오류나 이상한 화면을 그대로 복사(캡처)해서 Antigravity에게 "이거 왜 안 돼? 고쳐줘"라고 붙여넣으세요.

AI 프롬프트 요령 & 실습 미션

일정·계획 로직을 AI에게 맡길 때의 요령과 확장 과제
1

"화면"보다 "계산 순서"를 먼저

간트는 그림이 아니라 계산 결과입니다. 전진 계산 → 후진 계산 → 그리기 순서를 적으면 AI가 화면과 로직을 섞지 않습니다.

2

검산할 숫자를 함께 주기

"출시일 2027-01-04, SPI 0.79가 나와야 한다"처럼 정답을 같이 주면 AI가 스스로 틀린 곳을 찾게 할 수 있습니다.

3

미션 1: 일정 단축 제안

주공정 작업 중 겹쳐서 진행할 수 있는 쌍을 찾아 "겹침 −3일이면 출시 −3일"처럼 단축안을 제안합니다.

4
